# One-time recovery of an expired relay identity

Approved by the user on 2026-10-11 for the existing Tencent relay and subsequent Windows WAN validation.

The existing node is stuck in a requested TURN secret rotation (active/applied 1, desired 2), with an expired node certificate. Normal startup rejects that certificate and renewal cannot finish during the pending rotation. Restarting or clearing database fields would not complete the authenticated transaction.

Use a one-time maintenance example and a root-only Linux orchestration script. Keep the original node, key, identity epoch, sequence, pending renewal, runtime envelope, topology and audit history. The root script backs up the exact protected envelopes, stops and isolates the agent, obtains a fresh one-use enrollment token using the existing protected administrator credential, and submits the original CSR and configuration through the formal enrollment, approval and pickup APIs. The service-user helper accepts only a validated certificate for the original key and node. It verifies the trusted CA, name, SAN, validity and future renewal deadline using existing library rules, checks the original sealed-file hash, and uses the original secure store's atomic write. Neither runtime validation nor API authorization changes.

Keep tokens, receipts, credentials and raw envelopes out of stdout and repository artifacts. Persist a root-private recovery journal for resuming after partial API success. A failed certificate validation leaves local identity unchanged. After local installation, normal Agent handles the existing version 2 upload/drain/probe/commit and healthy heartbeat admission. Verify real server status and audit records before declaring recovery.

The HTTPS maintenance client uses the installed `/usr/bin/curl` with normal certificate, hostname and expiry validation against the protected original CA plus an empty root-private CA directory. This accommodates historical certificates rejected by Python's added X509 strict AKI requirement without disabling TLS verification. Credentials and JSON travel only in curl's stdin configuration; inherited proxy, trust, key-log and loader settings are excluded. Responses are limited to 1 MiB including headers and 30 seconds, redirects and extra status blocks are rejected, and errors contain only static codes. The loopback HTTP administrator API and normal Agent validation remain unchanged.

Retry a lost enrollment response using the same retained token and exact payload digest; the formal backend implements this idempotently. Reconcile an unknown approval outcome using the original receipt's repeatable pickup before attempting approval. Persist the `starting` stage before lifting the stop guard, so a retry accepts legitimate Agent sequence progress and never stops an Agent that has resumed. A crash after identity installation but before its result is journaled remains a deliberate fail-stop outcome: retain both exact backups and the stop guard for verified operator reconciliation; do not reinstall or discard the new identity automatically.

Tests cover missing identity, wrong certificate/key/CA/node, expired or due certificate, state/key preservation, stale original hash, missing/mismatched backup and write failure. Operator tests cover protected file boundaries, configuration preservation, API error redaction and crash-resume behavior. Actual WAN validation follows using the guest browser flow, real target consent, actual RTC route, decoded/presented video and signed input acknowledgment.
